# 从注意力算法研究到 FSA HLS 与 NM37 上板验证的暑期工作报告

## 报告说明

本报告系统整理暑期阶段围绕注意力计算加速所开展的研究与工程工作。工作起点并不是直接编写 HLS，而是依次阅读《Attention Is All You Need》、FlashAttention、FlashAttention-2 和 FSA，在理解注意力算法、存储访问优化、并行任务划分与脉动阵列复用思路之后，再进入 FSA 的硬件结构调研与 HLS 实现。

对 FSA 原工程的研究严格限定在 Scala/Chisel 硬件实现部分，重点关注 PE、CMP、Accumulator、SRAM、Execution Plan、Delayer 和 Controller 七类结构。随后，以这些结构为参照完成模块级 HLS 迁移、逐步集成、请求级控制、在线 softmax、DMA 顶层以及 Vivado 板级验证。

暑期工作的最终工程结果是：FSA HLS IP 已在 NM37 板卡的 Vivado 测试工程中完成固定测试向量的实际上板验证，板级测试通过。这里的“通过”表示当前计算 IP、时钟与复位、AXI-Lite 控制、片上测试存储以及固定向量计算路径能够在真实 FPGA 上正确运行；它不等同于已经完成可交付系统的完全部署。暑期内尚未完成最终外部存储与主机数据通路、驱动和运行时软件，也没有运行面向实际应用的完整软件负载。

此外，围绕 DATAFLOW 的流式重构属于在现有成果基础上提出的未来方向，不属于暑期已完成内容。本报告只在“未来方向”中讨论其动机、基本设想和验证要求，不将其纳入阶段成果、性能数据或完成时间线。

## 一、研究背景与总体目标

Transformer 的核心计算之一是缩放点积注意力。对于查询矩阵 Q、键矩阵 K 和值矩阵 V，基本形式为：

$$
S = \frac{QK^T}{\sqrt{d}},\qquad P = \operatorname{softmax}(S),\qquad O = PV
$$

其中，序列长度增加时，分数矩阵 S 和概率矩阵 P 的规模按序列长度的平方增长。传统实现往往把多个中间矩阵写回外部存储器，再由后续算子重新读入，导致大量数据搬运。对 FPGA 而言，问题不仅是乘加次数多，还包括片上存储有限、外部带宽有限、数据依赖复杂、softmax 需要归约，以及计算阵列利用率容易受到控制方式和数据排布影响。

因此，本项目的总体目标逐步明确为：首先理解注意力及其 IO 优化方法；其次分析 FSA 如何用一个可复用的脉动阵列覆盖注意力的多个计算阶段；然后把相关结构迁移到 HLS，建立从基础模块到完整请求的验证链；最后把 HLS IP 接入 Vivado，并在 NM37 板卡上完成真实硬件验证。

## 二、论文阅读与研究思路形成

### 1. 《Attention Is All You Need》：明确算法对象

第一阶段阅读《Attention Is All You Need》，重点不是复述 Transformer 的全部网络结构，而是建立后续硬件实现所需的计算认识。

首先，注意力的主体可以分解为两个大规模矩阵乘法和一个位于两者之间的按行 softmax。第一个矩阵乘法生成 Q 与 K 的相似度，softmax 把相似度变为归一化权重，第二个矩阵乘法再用这些权重对 V 加权求和。硬件设计不能只关注乘法器数量，因为 softmax 的最大值、指数、求和、归一化以及各阶段之间的数据保存同样决定系统结构。

其次，自回归场景需要 causal mask。对于第 i 个查询，只允许访问位置不晚于 i 的键。这意味着不同查询行的有效键数量不同，边界 tile 也可能只包含部分有效元素。若控制器只按完整矩阵块运行而不显式处理有效长度，就可能把无效位置带入最大值和指数和，造成错误结果。

最后，缩放因子通常为 $1/\sqrt{d}$。它必须与定点数格式、指数近似的输入范围和溢出策略一起考虑，不能被当作与实现无关的常数。

通过这篇论文，我们明确了硬件实现必须同时处理矩阵乘法、行归约、非线性函数、掩码、状态保存和最终归一化，不能把注意力简化为普通矩阵乘法加速。

### 2. FlashAttention：由算术优化转向 IO 感知

第二阶段阅读 FlashAttention。该工作的核心启发是：注意力加速的关键不只是减少算术操作，更重要的是减少高层存储器与片上快速存储器之间的数据传输。

FlashAttention 对 Q、K 和 V 进行分块，不再完整物化分数矩阵和概率矩阵，而是让每个 Q 块依次与多个 K、V 块交互。中间状态保存在更靠近计算单元的位置，从而减少外部存储访问。这个过程要求 softmax 能够在线更新。

设处理新键块之前，一行分数的最大值、指数和与未归一化输出分别为 $m$、$l$ 和 $O$；新块内部对应值为 $m_b$、$l_b$ 和 $O_b$。合并时可写为：

$$
m' = \max(m,m_b)
$$

$$
l' = e^{m-m'}l + e^{m_b-m'}l_b
$$

$$
O' = e^{m-m'}O + e^{m_b-m'}O_b
$$

在全部键块处理完成后，再以 $l'$ 对输出归一化。这个递推关系说明，不必保存完整注意力矩阵，只需为每个查询行维护最大值、指数和和输出向量。

对后续工程而言，这一认识直接决定了 CMP、Accumulator 和 SRAM 的存在理由：CMP 负责在线最大值，Accumulator 保存并更新 l 和 O，SRAM 保存跨块延续的状态。FlashAttention 因而成为从算法公式过渡到具体硬件状态机的关键桥梁。

### 3. FlashAttention-2：重新审视并行划分与非矩阵操作

第三阶段阅读 FlashAttention-2。它进一步指出，即使采用 IO 感知分块，若工作划分不合理，仍会因同步、共享状态和非矩阵操作占比过高而损失性能。

这篇论文带来的主要认识包括：应尽量减少循环内部的缩放、边界判断和重复状态变换；应让并行单元承担相对独立的工作，降低共享状态更新带来的同步；应使矩阵乘加结构保持稳定、规则和连续的数据流；对于不规则长度和 causal 场景，应在控制层准确限定有效元素，而不是让大量无效计算进入归约路径。

这些原则后来体现在 HLS 实现中：把阵列维度和数据宽度参数化；显式传递有效行列数；把比较、累加、延迟和存储分成独立模块；利用编译期信息减少运行期控制；并通过分层验证区分局部流水化与完整请求吞吐。

### 4. FSA：用单一阵列覆盖注意力的多个阶段

第四阶段阅读 FSA。相比前面三篇论文，FSA 更直接地回答了“如何把 FlashAttention 的数据流落实为硬件结构”。其关键思想是让同一个脉动阵列在不同阶段承担不同功能，而不是为 QK、softmax 相关运算和 PV 分别配置长期闲置的专用计算阵列。

从硬件角度看，一个注意力 tile 的处理并不是单一矩阵乘法，而是多阶段、带状态的过程。需要根据阶段改变 PE 的数据来源、乘加方式和结果去向；需要用 CMP 维护行最大值；需要用 Accumulator 更新指数和与输出；需要用 SRAM 保存跨阶段状态；需要用 Delayer 建立规则波前；还需要由 Execution Plan 和 Controller 把一条高层矩阵请求展开成逐拍动作。

FSA 的价值不仅是给出某个性能数字，更重要的是提供了一个可迁移的架构框架：数据通路负责规则计算，状态模块负责在线 softmax，控制平面负责决定何时读、何时算、何时写以及何时切换阶段。本项目后续的 HLS 迁移正是围绕这一框架展开。

### 5. 四篇论文之间的递进关系

四篇论文形成了清晰的研究链路。《Attention Is All You Need》定义注意力计算及其依赖；FlashAttention 说明分块与在线 softmax 如何降低 IO；FlashAttention-2 进一步优化循环组织和并行工作划分；FSA 则把这些思想映射为可复用脉动阵列、片上状态和逐拍控制。

因此，后续工程并不是对某篇论文的机械复现，而是把算法、IO、并行和硬件控制四个层次串联起来，再根据 HLS 与目标 FPGA 的特点逐层实现和验证。

## 三、FSA Scala/Chisel 实现调研

### 1. 调研范围与方法

FSA 原工程包含多个层次。本阶段只研究 Scala/Chisel 部分，不扩展讨论软件栈、系统仿真环境或其他非 Scala 实现。阅读重点集中在 PE、CMP、Accumulator、SRAM、Execution Plan、Delayer 和 Controller。

调研方法是从模块端口和状态开始，沿数据流追踪一条 Matrix 指令如何被拆成多个阶段，再反向确认每个阶段依赖哪些存储、计数器和有效信号。与单纯阅读算法伪代码相比，这种方法更容易暴露硬件真正需要解决的问题，例如同一状态在当前拍和下一拍之间的关系、阵列输入错位、bank 冲突、无效元素屏蔽，以及完成信号与输出有效信号的区别。

### 2. PE：多阶段复用的基础计算单元

PE 是阵列中的基本单元。其任务不是永远执行一种固定乘加，而是根据阶段选择操作数和累加路径。数据在相邻 PE 之间按节拍传播，局部寄存器保存当前操作数或部分和。

对 HLS 迁移而言，最重要的不是照搬寄存器名称，而是保持三个语义：每个逻辑步只消费规定的数据；结果在规定的下一逻辑步可见；阶段切换不会错误复用上一阶段的状态。这要求在 C++ 顺序语义与硬件并行语义之间建立明确映射。

### 3. CMP：在线最大值与掩码处理

CMP 面向 softmax 的最大值归约。它要在新分数到达时更新每一行的局部或全局最大值，并对 causal 或边界外元素进行屏蔽。

如果无效元素在比较阶段未被排除，它们可能改变最大值；最大值一旦错误，后续指数缩放和累加都会受到影响。因此，CMP 既是数值模块也是有效性控制模块。迁移时需要统一负无穷近似、有效标记、定点比较与掩码规则。

### 4. Accumulator：维护在线 softmax 状态

Accumulator 负责维护指数和 l、未归一化输出 O 以及旧状态到新状态的重缩放。它把 CMP 产生的新最大值与当前块结果结合起来，是实现在线 softmax 的核心。

这一模块的困难在于数据依赖链长：最大值变化会影响旧 l 和旧 O 的缩放，新块指数又影响新 l 与新 O。若定点位宽不足，可能出现饱和或精度损失；若流水级划分不当，则会形成关键路径；若状态读写次序不正确，则会把同一逻辑步的新旧数据混在一起。

### 5. SRAM：跨块状态与并行访问的载体

SRAM 保存 Q、K、V、m、l 和 O 等跨 tile 或跨阶段使用的数据。FSA 需要多 bank 组织，使不同 lane 或不同 PE 能够并行访问。

迁移时重点分析地址生成、bank 选择、读延迟、写使能和同拍读写关系。HLS 数组即使功能上正确，也不一定自动映射为期望的 BRAM 或 LUTRAM；数组过小、分区过强或访问端口过多，都可能导致寄存器化或资源复制。因此，存储结构必须与访问模式一起设计，并通过综合报告确认映射结果。

### 6. Delayer：建立脉动阵列波前

脉动阵列要求不同行或不同列的数据在不同时间进入阵列。Delayer 通过逐级延迟形成对角波前，使相应的 Q、K 或中间结果在同一 PE 中正确相遇。输出侧的延迟结构则负责把分散产生的结果重新对齐。

该模块算术简单，但对时序语义非常敏感。任何一级延迟少一拍或多一拍，都可能在小规模随机测试中表现为规则错位。因而需要用带明显位置特征的输入验证传播顺序，而不能只使用全零或全一数据。

### 7. Execution Plan：把矩阵请求展开为逐拍计划

Execution Plan 负责把高层矩阵指令转换为每个逻辑步的控制信息，包括当前阶段、索引、有效范围、读写地址、PE 模式、是否清零、是否累加以及是否提交结果。

它是算法循环与硬件控制之间的桥梁。矩阵维度、tile 数量、尾块有效元素和 causal 上界都必须在计划中体现。若计划的步数、边界或阶段转换存在一拍偏差，数据通路本身即使完全正确，也会产生错误结果。

### 8. Controller：执行计划并组织模块协同

Controller 接收请求、初始化状态、逐步发出计划项、等待或采集模块结果、更新计数器，并在整个事务完成后产生完成标志。它还需要处理启动握手，防止运行中重复接收请求，以及区分“最后一个输入已发出”和“最后一个输出已提交”。

在 HLS 中，Controller 最终对应一个请求级状态机。它必须既保持 Scala 设计的逻辑步语义，又符合 HLS 顶层协议和接口规则。因此，Controller 是模块迁移完成之后最重要的系统集成点。

### 9. 七类模块的整体关系

从整体上看，Execution Plan 决定每一逻辑步要做什么，Controller 决定计划何时执行并管理事务边界，SRAM 提供跨步骤状态，Delayer 把数据整理成阵列所需波前，PE 完成规则乘加，CMP 完成最大值和有效性处理，Accumulator 完成在线 softmax 状态更新。七者共同构成 FSA 的计算、存储与控制闭环。

## 四、HLS 迁移方法与基础规范

### 1. 分层迁移而非一次性重写

迁移采用自底向上的方式。先建立定点类型、接口结构和基础工具，再分别实现 PE、CMP、Delayer、阵列、Accumulator 和 Banked SRAM；模块通过后，依次组合为逐逻辑步核心、带 Execution Plan 的指令级核心、请求级核心和 DMA 顶层。

这种方式的优势是每一级都有独立可观察边界。若最终结果错误，可以判断问题来自算术、波前、状态更新、地址、计划还是请求协议，而不是在一个庞大顶层中盲目定位。

### 2. current/next 状态模型

Scala/Chisel 中的寄存器在时钟边沿统一更新，而普通 C++ 赋值具有顺序可见性。为了保持同步硬件语义，暑期实现采用 current/next 状态模型：一个逻辑步内只读取当前状态，把全部更新写入下一状态；逻辑步结束后再整体提交。

这一模型在软件执行时显得较为保守，但它清楚表达了硬件中“同一拍读取旧值、下一拍看到新值”的规则，是对照原 Scala 行为和建立功能基准的重要手段。后续任何性能优化都应先与这一基准比较，不能在优化过程中改变状态更新语义。

### 3. 定点数与数值近似

项目使用定点数表达输入、权重、中间乘积、指数和与输出。设计中区分外部数据位宽、乘法结果位宽和累加位宽，避免在每次乘加后过早截断。

指数函数不能简单视为理想实数运算。需要限定输入区间，选择近似方法，并规定超出范围时的饱和行为。除数和归一化也要防止零分母。验证时既比较最终结果，也检查位模式、符号扩展、截断和饱和，避免浮点打印值看似接近而底层定点行为已经不一致。

### 4. 验证层级

项目建立了四级验证体系。第一层是普通 C++ 功能测试，用于快速检查数学与状态机；第二层是 HLS C 仿真，用于确认顶层接口和综合语义；第三层是 C 综合与 RTL 协同仿真，用于检查资源、时序估算以及 C/RTL 一致性；第四层是 Vivado 仿真、综合、实现和真实板卡验证。

只有通过更高层验证，才能宣称更高层结论。C 仿真正确并不代表 RTL 一定正确，HLS 时序估算也不代表完整 Vivado 系统已经完成布局布线，而工程文件齐备更不等于上板通过。

## 五、基础模块的实现与验证

### 1. PE

PE 首先完成标量乘加和状态更新，再扩展到不同阶段的输入选择和结果转发。测试覆盖正负数、零、累加保持、清零、有效和无效输入，并检查定点位模式。随后将多个 PE 组合进阵列，确认单元行为在空间连接后保持一致。

### 2. CMP

CMP 实现逐行最大值更新、有效元素判断和 causal 屏蔽。测试重点覆盖首个有效值、全部无效、最大值位于不同位置、负数输入、尾块以及 causal 边界。通过这些测试确认掩码在比较之前生效，旧最大值和新块最大值能够按预期合并。

### 3. InputDelayer 与 OutputDelayer

输入延迟器把各 lane 的数据按行列偏移后送入阵列，输出延迟器重新对齐阵列结果。测试使用位置相关的非对称数据追踪每个元素，逐步核对进入和离开阵列的时间。该阶段修正了若干容易导致结果整体偏移的索引与边界问题。

### 4. 4×4 Systolic Array

阵列由 16 个 PE 构成。早期实现虽然功能正确，但综合后未必形成期望的空间并行。后续通过展开规则计算、分区局部数组和调整接口，使 16 个 PE 能够并行工作，并对不同矩阵尺寸和尾块进行验证。

阵列测试不只比较最终矩阵结果，还观察逻辑步数、输入波前、部分和传播和输出有效时刻。这样可以区分数值错误与时序错位。

### 5. Accumulator

Accumulator 逐步加入最大值重缩放、指数和更新、输出向量更新和最终归一化。测试覆盖最大值不变、最大值升高、多个键块连续合并、部分有效 lane 和接近数值边界的输入。

这一阶段确认在线 softmax 可以只依靠 m、l 和 O 的有限状态完成跨块更新，不需要保存完整分数矩阵。同时也发现，指数近似、乘法位宽与累加位宽必须联合选择，否则误差会在多个块之间累积。

### 6. Banked SRAM

Banked SRAM 采用多 bank 组织，支持多个 lane 的并行读写。验证覆盖地址到 bank 的映射、不同 bank 并发、同 bank 访问、边界地址、写后读和复位后的状态。

综合分析表明，小型数组可能被映射为 LUT 或寄存器，而不是天然进入 BRAM。这并非单纯的工具问题，而是数组容量、端口需求、分区方式和访问规律共同作用的结果。因此，资源报告被作为功能测试之外的必要证据。

## 六、FSA 核心的逐级集成

### 1. 逐逻辑步核心

首先把 Delayer、阵列、CMP、Accumulator 和 SRAM 连接为单步核心。外部测试环境显式推进逻辑步，便于在每一步检查当前状态、下一状态、读写地址和有效信号。这一层主要用于验证模块连接是否保持 Scala 的同步语义。

### 2. Execution Plan 迁移

随后把矩阵维度、tile 索引、阶段和边界规则编码为执行计划。测试逐项核对计划长度、首尾步骤、阶段切换、尾块和 causal 有效范围，并确认地址不会越界。

Execution Plan 的引入使核心从“由测试程序逐拍操纵”转变为“根据一条高层请求自主生成逐拍控制”。它也是后续请求级 Controller 能够稳定工作的前提。

### 3. 指令级核心

在指令级核心中，Controller 接收一条 Matrix 指令，初始化计数器和状态，按 Execution Plan 驱动单步核心，并在最后结果写回后结束事务。此阶段重点处理启动、忙、完成和输出有效之间的关系。

测试覆盖连续指令、不同尺寸、非整 tile 和 causal 模式。对连续事务尤其检查前一条指令的状态是否泄漏到下一条指令，以及完成信号是否只在规定时间出现。

### 4. 请求级核心与多块在线 softmax

请求级核心进一步覆盖完整注意力请求，使同一查询块可以连续处理多个键值块，并在片上保存 m、l 和 O。每个新块完成后，Accumulator 用新的最大值重新缩放旧状态，再合并新块结果。

这一阶段完成了单块、双块、多块、尾块和 causal 场景的功能验证。其意义在于证明系统不是只会计算孤立的 4×4 示例，而是能够沿序列维度维护在线 softmax 状态。

## 七、DMA 顶层与端到端闭环

### 1. 顶层接口与数据布局

DMA 顶层为 Q、K、V 和 O 建立外部存储访问接口，并通过 AXI-Lite 接收配置和启动命令。控制参数包括序列长度、头维度、缩放和 causal 模式等。数据布局需要明确元素顺序、定点表示、对齐方式和输出区域，确保主机、HLS 与 RTL 对同一地址具有一致解释。

### 2. 完整序列测试

端到端测试从外部存储模型读取 Q、K 和 V，经过请求级核心完成分块注意力，再把 O 写回输出区域。测试覆盖短序列、跨多个 tile 的序列、非整 tile、causal 与非 causal 模式，并检查输出边界，防止越界写破坏相邻区域。

参考结果由独立的软件金标准产生。比较时既考虑定点量化允许的误差，也检查输出元素数量、写地址和完成状态。这样可以避免只比较少量样本而遗漏控制错误。

### 3. 单核心复用问题与修复

请求控制曾因函数层次和调用结构导致综合工具推断出多份核心实例。该问题不会直接造成 C 仿真错误，却会显著放大 DSP、LUT 和寄存器资源，使设计难以扩展。

通过重新组织请求状态机，让所有请求阶段共享同一个 FSA 核心，并用显式阶段状态决定当前任务，消除了意外复制。综合结果从多份核心收敛为单核心结构，DSP 使用量降至约 303 个，同时保持完整序列功能和协同仿真一致性。这一修复说明，HLS 中的顺序调用写法不必然代表硬件时分复用，资源共享必须通过综合层次和实例报告确认。

### 4. HLS 阶段结论

到这一阶段，项目已经形成从外部输入、请求控制、分块计算、在线 softmax 到输出回写的完整 HLS 闭环。多个层级通过了 C 仿真，关键顶层完成了综合和 RTL 协同仿真，并解决了资源意外复制问题。

不过，局部循环达到较小启动间隔，并不代表完整请求可以同样速率连续进入。当前架构仍以逐逻辑步状态推进为主，请求级延迟受到阶段数量、状态提交和存储访问共同影响。因此，报告将功能正确性、局部流水化、完整请求吞吐和板级性能严格区分。

## 八、NM37 Vivado 上板验证

### 1. 上板目标与验收边界

NM37 上板的首要目标是证明 HLS 计算 IP 可以离开 HLS 仿真环境，在真实 FPGA 上由 Vivado 工程正确例化、复位、启动并产生预期输出。为了降低首次板测的不确定性，测试采用固定向量和片上存储，不把外部高速数据通路、操作系统驱动和应用软件同时引入。

验收范围包括：HLS IP 能被 Vivado 正确识别；时钟和复位能够稳定驱动核心；AXI-Lite 控制寄存器可以完成启动和状态读取；片上测试存储能够提供 Q、K、V 并接收 O；固定测试向量的输出与预期一致；测试结束状态和边界保护正常。

不在本次验收范围内的内容包括：最终 XDMA 或其他主机高速传输链路、外部 HBM/DDR 的完整数据通路、Linux 驱动、用户态运行时、模型框架接入、真实网络输入和持续软件负载。

### 2. 板测工程组织

板测工程围绕固定控制器、HLS IP、片上测试 RAM、时钟复位、VIO 和 ILA 组织。固定控制器负责准备测试数据、配置请求、启动计算、等待完成并检查结果；VIO 用于人工触发和观察总体状态；ILA 用于捕获关键握手、地址、完成和错误信息。

这种组织把首次上板问题限制在可观察范围内。如果计算未开始，可以检查复位、启动和空闲状态；如果计算结束但结果不对，可以检查地址、有效信号和输出写入；如果一直不结束，可以检查 Controller 状态和等待条件。

### 3. 验证过程

首先在 HLS 侧确认导出的 IP 接口、控制协议和目标配置。随后在 Vivado 中建立工程，连接时钟复位、控制接口和片上存储，并为关键状态加入可观察信号。工程先进行行为检查，再进行综合、实现和 bitstream 生成。完成下载后，通过板上控制路径发起固定向量测试，并读取完成状态、错误状态和输出数据。

在这一过程中，重点检查了复位极性与同步关系、启动脉冲宽度、完成信号保持方式、AXI-Lite 地址映射、片上 RAM 的读写时序，以及输出区域是否出现越界修改。板级判断不依赖单一 done 信号，而是结合输出内容和边界保护进行确认。

### 4. 最终结果

NM37 上的 Vivado 固定向量板级测试通过。这是暑期工作达到的最高验证层级，表明 FSA HLS IP 及其基本 Vivado 包装已经能够在真实 FPGA 上运行，核心控制和固定数据计算路径具备板级可行性。

同时必须明确，该结果是面向计算 IP 的受控板测，不是完整加速系统部署完成。项目尚未完成最终外部存储与主机传输链路，尚未形成驱动、运行时和应用层调用的完整软件栈，也没有加载真实模型或应用负载进行端到端运行。因此，当前成果应表述为“NM37 Vivado 上板测试通过，完全部署和软件负载尚未完成”。

## 九、关键技术问题与经验总结

### 1. 逻辑步不等于物理时钟

软件测试中的一次 step 是架构语义上的逻辑推进，综合后可能包含多个物理时钟，也可能因流水化而与其他操作重叠。项目通过 current/next 模型保证逻辑正确，再用综合和 RTL 报告判断实际延迟，避免把 C++ 循环次数直接当作硬件周期数。

### 2. 局部 II 不等于系统吞吐

某个 PE 或循环达到 II=1，只说明该局部流水线能够每拍接收一次迭代。完整请求还受到控制状态、阶段切换、存储访问和输出提交限制。性能结论必须分别报告局部循环、tile、请求和系统级吞吐。

### 3. 功能正确不代表资源结构正确

七份核心复制问题说明，C 仿真完全正确时，硬件结构仍可能严重偏离设计意图。项目由综合层次和资源报告发现问题，再通过单核心请求状态机实现真正的时分复用。今后的每项重构都应同时检查功能、实例数和资源映射。

### 4. 时序切割必须形成真实寄存器边界

仅增加临时变量或拆分表达式，不一定能在 RTL 中形成寄存器。若同一循环迭代中的生产者和消费者仍被组合，关键路径并不会缩短。需要结合调度报告和 RTL 层次确认运算是否跨周期分割。

### 5. 存储映射必须服从访问模式

数组分区可以增加并行端口，也可能使存储完全寄存器化。强制 BRAM 映射若与端口需求冲突，工具可能复制 RAM 或无法满足 II。正确做法是先明确每拍访问数、bank 规则和容量，再选择分区与资源约束。

### 6. 复位、上电值和静态状态需要显式管理

C 仿真常从理想初值开始，真实 FPGA 上的静态变量、RAM 和跨事务状态则必须由复位或初始化流程保证。NM37 板测进一步说明，启动前清理状态、复位释放顺序和 done/error 的保持策略都属于功能的一部分。

### 7. 接口协议也是算法正确性的一部分

若启动在 busy 期间被重复采样、done 脉冲过短、地址宽度不一致或字节选通信号处理错误，即使计算核心正确，系统仍无法可靠工作。因此，AXI-Lite 控制、存储边界、状态寄存器和重复运行测试与数值测试具有同等重要性。

### 8. 上板通过不等于完全部署

固定向量板测主要消除 IP、时钟复位、控制和基本计算路径的不确定性。完全部署还要求真实数据通路、外部存储、驱动、运行时、错误恢复、连续任务和应用负载全部闭环。明确这一区别可以避免高估阶段成果，也为下一步工作提供清晰验收标准。

## 十二、未来方向

### 1. DATAFLOW 流式重构

DATAFLOW 重构是暑期工作之后的未来方向，不属于本报告所列已完成成果。提出这一方向的原因是，当前 current/next 与请求级状态机非常适合建立功能基准，但状态整体提交、阶段串行推进和中间缓冲可能限制请求吞吐，并带来额外存储或多路选择开销。

未来可以研究以单组 4×4 计算阵列跨阶段复用，并在阶段之间通过显式数据流 token 传递工作。生产者和消费者必须具有可证明的一致 token 数；无效 bubble 也应携带有效性信息继续流动，不能因条件分支少写数据而造成阻塞。CMP、Accumulator 和 SRAM 需要围绕驻留状态重新组织，使最大值、指数和与输出更新能够在不复制整个核心的前提下并行重叠。

该方向的评价不能只看局部 II 或单次综合资源。至少需要依次完成独立金标准 C 仿真、HLS C 仿真、C 综合、RTL 协同仿真、FIFO 深度与死锁检查、Vivado 时序和资源分析，最后重新在 NM37 上板验证。只有所有层级通过，DATAFLOW 才能从设想转化为正式成果。

### 2. 完整硬件部署

下一步需要选择并固定最终主机到 FPGA 的数据通路，完成外部存储控制、地址空间、缓存一致性或显式同步、异常处理和连续事务。随后进行完整系统的综合、实现、时序收敛、功耗分析和长期稳定性测试。

固定向量板测中的片上 RAM 应逐步替换为真实部署的数据来源，同时保留可回退的诊断模式。每引入一个新层次，都应先建立独立回环或自检，再与 FSA 计算核心组合，避免同时调试传输、存储和计算。

### 3. 软件栈与实际负载

需要补充驱动、用户态运行时和主机调用接口，明确数据量化、内存分配、参数配置、启动、等待、超时和错误恢复。应建立可重复的软件金标准，并让同一输入在 CPU 参考实现和 FPGA 上运行后自动比较。

在基础软件链路稳定后，再加载具有代表性的注意力工作负载，包括不同序列长度、head dimension、causal 模式、连续请求和批处理。最终评价应包含正确率、端到端延迟、吞吐、传输开销、板上功耗和重复运行稳定性，而不能只使用核内周期或单个固定向量。

### 4. 规模扩展与资源平衡

更大 head dimension、序列长度或多核心扩展会放大 SRAM 容量、bank 端口、路由拥塞和归约树时序问题。未来需要联合探索阵列规模、tile 形状、数据位宽、存储层次和工作频率，并分别报告核内资源与完整系统资源。

扩展时应坚持先验证单核心复用与单请求正确性，再增加并行度。任何通过复制核心获得的吞吐提升，都必须同时评估外部带宽是否能够供数、布局布线是否可收敛，以及软件是否能够持续提交任务。

## 结论

暑期项目完成了一条较为完整的研究与工程路径：从《Attention Is All You Need》出发理解注意力计算，经过 FlashAttention 和 FlashAttention-2 掌握 IO 感知分块与并行划分，再通过 FSA 研究单一脉动阵列跨阶段复用；随后聚焦 FSA 的 Scala/Chisel 实现，系统分析 PE、CMP、Accumulator、SRAM、Execution Plan、Delayer 和 Controller，并将这些结构逐级迁移到 HLS。

在工程层面，项目完成了基础模块、4×4 阵列、在线 softmax、执行计划、请求控制和 DMA 顶层，建立了从模块 C 测试、HLS 仿真、综合、RTL 协同到 Vivado 板测的分层验证方法；发现并解决了定点位模式、波前对齐、状态语义、边界、存储映射和多核心意外复制等问题。最终，FSA HLS IP 在 NM37 的 Vivado 固定向量工程中实际上板测试通过。

这一结果证明了当前 FSA HLS 计算路径的板级可行性，但项目尚未完成完整部署，也没有完成最终外部存储和主机传输链路、驱动与运行时软件，更未加载真实应用软件负载。DATAFLOW 流式重构同样属于未来方向，不应计入暑期完成项。因而，对当前阶段最准确的总结是：算法理解、Scala 架构分析、HLS 原型和 NM37 受控上板验证已经完成；从可运行计算 IP 走向可部署、可由软件持续调用的完整 FPGA 加速系统，仍是下一阶段的主要任务。
