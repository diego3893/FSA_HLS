## 1. `SCHED 204-65` 到底由什么触发

### 1.1 我能确证的

- 该警告的原文与语义：`Unable to satisfy pipeline directive for function 'runPeArray': control-flow is too complicated to be pipelined.` 属于 SCHED 204 流水调度组；当工具"无法按用户指定 II 建立流水时"，官方文档给出的行为是**发警告并改成它能做到的最小 II**：
  > "If the Vitis high-level synthesis tool cannot create a design with the user-specified II, it issues a warning and creates a design with the lowest achievable II." **[文档]** [Vitis Tutorials, Pipelining for Throughput](https://xilinx.github.io/Vitis-Tutorials/2021-2/build/html/docs/Hardware_Acceleration/Design_Tutorials/06-cholesky-accel/03-Algorithm_Acceleration/docs/module2_pipeline/README.html)
- 官方错误码页（`HLS 200-880 Pipeline Constraint Violation`）是这一族问题的指导入口，但它已 301 跳转到 `docs.amd.com`，**我在本会话环境下无法读取其正文**（见第 6 节）。链接：[hls-guidance/200-880](https://www.xilinx.com/htmldocs/xilinx2021_2/hls-guidance/200-880.html) **[文档·仅确认存在，未读到内容]**

### 1.2 与现象直接相关的三条官方硬约束

1. **被流水层级以下的所有循环必须完全展开；含变量边界的循环直接阻止流水**：
   > "IMPORTANT: When a loop or function is pipelined, Vivado HLS unrolls all loops in the hierarchy below the function or loop. If there is a loop with variable bounds in this hierarchy, it prevents pipelining."
   > "TIP: When a loop or function is pipelined, any loop in the hierarchy below the loop or function being pipelined must be unrolled." **[文档]** [UG902 v2015.1 Code Style / Functions and Loops（经 CSDN 镜像全文引用）](https://blog.csdn.net/weixin_30305735/article/details/98939371) · [UG902 原始 PDF](https://fpga.eetrend.com/files-eetrend-xilinx/forum/201703/11222-29186-ug902-code_style-vivado-high-level-synthesis.pdf)
2. **流水化层级越高，需要调度的算子数成倍增长**。UG902 用 20×20 的例子给出量级：流水内层 ≈ 1 个乘法器；流水外层 → 20 份；流水**函数** → 400 份，并明确写"极不可能生成 400 个乘法"，且即使双口 RAM 每拍也只能取 2 个元素；资源从"<100 LUT"涨到"thousands of LUTs and registers"。**[文档]** 同上
3. **不完美循环嵌套不能被 flatten**（UG1399 v2022.2 p.93 邻近条目，搜索服务返回该页同时命中 "This issue is typically caused by arrays"）：**[文档·只读到片段]**
   - "Vitis HLS cannot flatten imperfect loop nests" — [UG1399 (v2022.2) p.93](https://www.xilinx.com/content/dam/xilinx/support/documents/sw_manuals/xilinx2022_2/ug1399-vitis-hls.pdf#93#10)
   - "This issue is typically caused by arrays" — [UG1399 (v2022.2) p.93](https://www.xilinx.com/content/dam/xilinx/support/documents/sw_manuals/xilinx2022_2/ug1399-vitis-hls.pdf#93#11)
   - 同页还有 `pragma HLS PIPELINE II=1` 与 pipeline-loops=6 的条目，可确认这一页就是 PIPELINE 指令的说明/限制页：**[文档]** [UG1399 p.93 同页条目](https://www.xilinx.com/content/dam/xilinx/support/documents/sw_manuals/xilinx2022_2/ug1399-vitis-hls.pdf#93#9)、[#93#8](https://www.xilinx.com/content/dam/xilinx/support/documents/sw_manuals/xilinx2022_2/ug1399-vitis-hls.pdf#93#8)
4. **社区同题帖（标题即结论，正文我读不到）**："Pipeline complexity too great" — [AMD Adaptive Support 帖](https://adaptivesupport.amd.com/s/question/0D52E00006hpXTWSA2/pipeline-complexity-too-great?language=en_US) **[社区·仅标题]**
5. **大 fan-in 数组索引 → 大 multiplexer → QoR/运行时间恶化**（官方社区帖标题所反映的已知问题）："Why accessed through nonconstant indices on dimension 1 which may result in long runtime and suboptimal QoR due to large multiplexers?" — [AMD 社区](https://adaptivesupport.amd.com/s/question/0D52E00006krCTxSAM/why-accessed-through-nonconstant-indices-on-dimension-1-which-may-result-in-long-runtime-and-suboptimal-qor-due-to-large-multiplexers?language=en_US)、[Array Partitioning long runtime and suboptimal QoR due to large multiplexers](https://adaptivesupport.amd.com/s/question/0D52E00006hpjgTSAQ/array-partitioning-long-runtime-and-suboptimal-qor-due-to-large-multiplexers?language=en_US) **[社区·仅标题]**
6. **可综合代码里写明的限制**：在 RTL region（未内联的子函数）内部，不能自由地添加/移动流水级 —— "pipeline retiming and other transformations like re-timing, and register balancing cannot be used within an RTL region." **[文档]** [UG1399 v2022.2 p.93 命中片段](https://www.xilinx.com/content/dam/xilinx/support/documents/sw_manuals/xilinx2022_2/ug1399-vitis-hls.pdf#93)（原文出处为函数内联/层次化相关章节）

### 1.3 回答"是元素数、操作数、控制结构还是端口数"

**没有官方文档给出 `204-65` 的定量阈值。** 我能给的最诚实结论是：

- 它是**流水调度失败的总出口**，触发面是"这一拍（或这 II 拍）内需要被同时调度进一个流水体的**行为图规模**"，而不是其中某一项单独指标。UG902 把三件事写成了因果链：流水层级↑ → 下层次全部展开 → 需要调度的运算/数组访问数↑ → 可能"极不可能"生成；再叠加"变量边界循环直接阻止流水"和"不完美嵌套不能 flatten"，共同构成"控制流太复杂"。**[文档+推断]**
- 对应到本项目的具体机制（**[推断]**，依据本地源码 `src/stream/split_d/split_d_compute.cpp:90-134` 与 `#15.1` 的日志）：
  - `runPeArray` 是 `INLINE off` 的独立函数，函数级 `#pragma HLS PIPELINE II=PE_ARRAY_II`（D=16 时 II=5）。函数级流水的"迭代体"= 整个函数体。
  - 函数体里 `bank` 循环与 `offset` 循环都是 `UNROLL`，`peBankMacUnit` 又被 `HLS 214-131` 内联进去（日志原文见 `PROJECT_CONTEXT.md#15.1`），因此**流水体里是 N 个无分支的 `peMacUnit` 副本 + 位模式转换 + 全 partition 数组的读写**。
  - D=16 相对 D=4 真正变化的不只是"更多 MAC"：**跨函数边界的数组端口总位数**从 4×(16×~64bit) 量级涨到 16×(256 元素) 量级，同时 `node_pe/node_b/node_c/node_result` 全 `complete partition` 又要为每次 bank 调用造出独立的选择器树。这三者（算子数 × 端口数 × 选择器）共同把一拍的行为图推到工具放弃。
  - **一个重要更正**：`#15.1` 说"单拍体内展开了 64 个 `peMacUnit`（bank 4 × 组内行 4 × 列 16）"。按**当前本地源码**（`split_d_internal.hpp:28-35`：D=16 时 `PE_BANK_ROWS=1`，`PE_BANK_NODES=16`；`bank` 循环步长 = `PE_BANK_ROWS` = 1，只有 1 次迭代）以及 `#15.1` 自己贴的日志 `Unrolling loop 'VITIS_LOOP_80_3' ... with a factor of 16`，D=16 一击内是 **1 个 bank × 16 个 PE**，不是 64。这个差别会影响第 5 节的方案选择，建议核对被测 commit。**[本项目实测/推断]**

## 2. 让大阵列可综合的推荐结构（按"结构性"从强到弱）

### 2.1 官方/论文层面的现成答案

| 结构 | 关键做法 | 来源 |
|---|---|---|
| **阵列按块平铺 + 只流水内层** | AutoSA 先把最外层可交换循环带做 tiling（如 (4,4,4) → 4×4 阵列），再用 strip-mine + 置换把并行点循环放到最内层以获得 II=1 | **[论文/文档]** [AutoSA: Constructing and Optimizing a Systolic Array](https://autosa.readthedocs.io/en/latest/tutorials/optimize_array.html) |
| **I/O 层次聚类（localize I/O）** | "this architecture may not be scalable as the data are scattered directly from the external memory which causes high fan-outs and could lead to routing failure" → 用 daisy-chain 的 L1/L2/L3 I/O module 聚类把 fan-out 降到 1 | **[论文/文档]** 同上 |
| **每个 PE 独立函数 + 本地小缓冲 + stream 互连** | 每 PE 只有 `aBuffer[2*kInnerTilesN]` 和 `cBuffer[...][kComputeTileSizeN]`，只对小的 compute-tile 循环加 `PIPELINE II=1`+`LOOP_FLATTEN`，PE 之间走 `Stream<>`，顶层 `DATAFLOW` | **[代码]** [gemm_hls kernel/Compute.cpp](https://cdn.jsdelivr.net/gh/spcl/gemm_hls@master/kernel/Compute.cpp) · [kernel/Top.cpp](https://cdn.jsdelivr.net/gh/spcl/gemm_hls@master/kernel/Top.cpp) |
| **把阵列做成"位移寄存器"逐拍推进，而不是一拍算完** | 16×16 阵列用 `inA/inB` 移位 + 条件注入 + 无条件 `inC[i][j] += inA*inB`，放在一个 `PIPELINE` 循环里，走 94 拍 | **[代码]** [ViT-Accelerator q_matmul_k_function.cpp](https://github.com/kabazoka/ViT-Accelerator/blob/main/hls_source/q_matmul_k_function.cpp) |
| **官方库的规模经验值** | Vitis BLAS L2 GEMM：systolic array 尺寸按外部存储器位宽设定，"for single-precision floating point GEMM and 512-bit DDR interface, the systolic array size is 16 x 16"；外围是 data mover + transpose + double buffer | **[文档]** [Vitis BLAS L2 GEMM Kernel](https://xilinx.github.io/Vitis_Libraries/blas/2022.1/user_guide/L2/L2_gemm_content.html) |
| **矩形 row-wise 数据流**（本项目方向） | SWAT 批评方阵："the systolic array's square structure requires square tiling of the input and the intermediate matrices. This tiling is suboptimal for row-wise SoftMax operations, necessitating supplementary computations outside the accelerator's capabilities." 对应做法：row-major dataflow + kernel fusion + input-stationary FIFO | **[论文]** [SWAT (DAC'24), §2.3](https://ar5iv.labs.arxiv.org/html/2405.17025) |
| **单阵列内跑完全部 5 个阶段** | SALO 用同一组 PE 完成 QK→exp→行求和→归一化→PV：QK 是 output-stationary，行求和是**横向 ripple 和**（左边 PE 传部分和给右边），PV 是 weight-stationary；每 PE 1 个定点 MAC + 1 个 `Reg_acc`；行和倒数在行尾算完再广播回整行 | **[论文]** [SALO (DAC'22), §5.1](https://ar5iv.labs.arxiv.org/html/2206.14550) |

### 2.2 `ARRAY_PARTITION` 粒度策略

- 语义（官方）：`complete` 把数组完全拆成独立元素/寄存器；`block`/`cyclic` 按维度分块或轮转切分成若干小数组。**[文档·片段]** [Vitis Application Acceleration Development, "complete: Complete reshaping decomposes the array into temporary individual elements…"](https://www.eetrend.com/files/2019-10/wen_zhang_/100045696-82978-vitis-application-acceleration.pdf)
- 取舍规则（我读到的定性描述 + **[推断]**）：`complete` 让所有元素同拍可读，代价是寄存器 + 大规模 mux 树（见 §1.2 第 5 条社区帖标题）；`block`/`cyclic` 只在需要"每拍固定几个端口"时用，端口少、但每拍可访问元素数受限。UG902 的 20×20 例子已经把这条量化：即使双口 RAM，每拍也只能取 2 个元素。**[文档]**
- **与 204-65 的关系 [推断]**：把 `complete` 换成 `block/cyclic` 能减少端口与 mux，但**不会自动解决 204-65**，因为 204-65 是"流水体过大/控制流过杂"的调度问题，不是端口冲突（端口冲突的正常表现是 II violation + `HLS 200-880`，本项目已有多次实测：`docs/综合报告/fsa_core_request综合报告.md:220`）。

## 4. 开源 HLS attention/GEMM 加速器的实际阵列组织

1. **spcl/gemm_hls**（纯 Vitis HLS，GEMM，FPGA'20）— [仓库](https://github.com/spcl/gemm_hls)
   - 一维 N 方向 PE 链：`ComputeTilesN` 个 `ProcessingElement` 由 `#pragma HLS UNROLL` 例化，PE 间用 `Stream<ComputePackN_t>` 线性传递 A，B 广播，C 回流。
   - 每个 PE **只有本地小缓冲**：`aBuffer[2*kInnerTilesN]` + `cBuffer[kInnerTilesN*kInnerTilesM][kComputeTileSizeN]`（`complete dim=2`）。
   - 只有 **compute-tile 的小循环**加 `PIPELINE II=1` + `LOOP_FLATTEN`；顶层用 `DATAFLOW` 组织 Read/Transpose/Feed/PE 链/Write。
   - 规模：`MM_PARALLELISM_N=32, MM_PARALLELISM_M=8`；实测 462 GFLOPS（half，VCU1525）；扩展瓶颈是跨 SLR 布线。
   - 关键点：**没有任何"单函数调度 256 个 PE"的地方**，流水边界永远套在小循环上。
2. **kabazoka/ViT-Accelerator**（Vivado/Vitis HLS 2022.1，ViT 注意力，U50）— [仓库](https://github.com/kabazoka/ViT-Accelerator)
   - `mmult` 用 16×16 tile：`subA[16][64]`、`subB[64][16]`、`inC[16][16]`、`inA/inB[16][16]` 全部 `complete` partition。
   - 阵列是**逐拍位移**的 systolic：每拍 `inA` 右移、`inB` 下移、条件注入新数据、然后 `inC[i][j] += inA[i][j]*inB[i][j]`；整段 94 次迭代带 `#pragma HLS PIPELINE`。
   - 仓库自带 study journal 记录了与本项目同类的坑："Since there are many sub-loops inside the function, it is impossible to directly use the pipeline rewind pragma"（作者亲述）。
   - 注意：这是**学生项目**，README 自述"actual host code has not done yet"，请当组织结构参考、不要当性能权威。
3. **UCLA-VAST/AutoSA**（systolic array 编译器，FPGA'21）— [仓库](https://github.com/UCLA-VAST/AutoSA) · [文档](https://autosa.readthedocs.io/en/latest/tutorials/optimize_array.html)
   - 空间维只取最外层 permutable band 里依赖距离 ≤1 的循环；tiling factor 决定阵列维度（示例 4×4）；latency hiding 用 strip-mine+置换消掉 MAC 的 loop-carried dependence 以拿 II=1。
   - 生成的 PE 是"小 MAC + 本地 buffer"，I/O 由 L1/L2/L3 聚类网络供给。
4. **SALO (DAC'22)** — [ar5iv](https://ar5iv.labs.arxiv.org/html/2206.14550)：32×32 PE 阵列 + 1 个 global PE row + 1 个 global PE column；每 PE 1 个定点 MAC + 1 个 `Reg_acc`；QK output-stationary、行和横向 ripple、PV weight-stationary。**注意：它是 Chisel 写、Synopsys DC + FreePDK 45nm 综合的 ASIC 设计**，不是 HLS——在 HLS 上能否同样流水没有证据。
5. **SWAT (DAC'24)** — [ar5iv](https://ar5iv.labs.arxiv.org/html/2405.17025)：FPGA + row-major dataflow + kernel fusion + input-stationary 固定长度 FIFO；用"把 softmax 分母挪到 PV 之后"的改写实现三算子融合。

**我没能验证的**：我没有找到一个**公开的、基于 Vitis HLS 的、含 256 PE 以上 2D 阵列的 attention/GEMM 实现**并附其 CSynth 报告与 II 数据。因此"256 PE 全并行在 HLS 上确实可行"这一点**目前没有直接先例证据**。**[缺口]**

## 5. 对本项目的排序建议

先给一段**前提修正**（很重要）：本项目 D=16 的 `runPeArray` 单拍体内的 `peMacUnit` 数，按当前本地源码是 16 个（1 bank × 16 节点），不是 `#15.1` 写的 64 个。而 D=4 时同样是 16 个 `peMacUnit`（1 bank × 16 节点）却能过。**这说明纯"MAC 数量"不是唯一变量**；D=16 真正暴涨的是 `pe/operand_b/operand_c/result/computed` 这几个 `PE_DIM×PE_DIM` 数组的跨边界端口位数（4× 每维 → 16 倍元素）与选择器规模，以及整体操作图（1.1–1.4M 指令）。这正好对应 UG1399 p.93 那条 "This issue is typically caused by arrays"。**建议在动手前先用一次 CSynth 的 RTL 层次 + 端口宽度确认这一点。**

### 建议 A（首选，置信度 **medium-high**）：把"阵列求值"从"函数级流水"改成"每个 PE 每拍只做固定小事的紧凑循环流水"

- 做法：不再让 `runPeArray` 作为"函数级流水 + 全展开"的巨型单拍体。改成：**PE 状态（`reg`/`score_acc`）仍是那唯一一份 256 元素原地状态**，但外层是一个**固定 trip count 的循环**（遍历 256 个 PE，或遍历 D×P 的 P 维），循环体里只有：数组读 → 1 次 fp16×fp16→fp32 MAC → 数组写，**无分支、无内层未展开循环、无 `if`**；`#pragma HLS PIPELINE II=<一或几拍>` 加在这个小循环上。
- 依据：UG902 明确"流水函数之下所有循环必须展开/不能有变量边界"，而**流水一个内层小循环是最省面积、最稳的做法**（同一例子：内层 <100 LUT vs 函数级 ~400× 逻辑）**[文档]**；ViT-Accelerator 与 gemm_hls 都是这个形状 **[代码]**；AutoSA 的 latency hiding 也是把点循环 strip-mine 到最内层再 unroll 以拿 II=1 **[论文]**。
- 代价：一片的 MAC 数从 256 降到 P（例如 P=16 或 32），要 DIM_BLOCKS×256/P 拍才能算完一轮。要满足项目目标（QK/ROW_SUM II≤5、PV II=1），**P 必须 ≥ 52（256/5）才能让 QK 侧不成为瓶颈**；那意味着每拍 52 个 MAC —— 比 D=4 的 16 个多，但控制流是"一条无分支直线"，规模问题从"控制流复杂度"变回"时序/资源"。这是本方案唯一的真实风险：**7.300 ns 是由 256 个 PE 的总门级深度和布线决定，不因改结构而自动变松**。
- 验证判据：CSynth 报告里该循环 achieved II ≤ 5；RTL 里 PE 实例数 = 256（不重复）；DSP 数 ≈ 256（每 PE 1 个 fp16 乘 + fp32 加，见本地 `fsa::peMacUnit` in `include/fsa/arithmetic.hpp:47`）。
- 缺什么证据：D=16 下"52 个无条件 MAC 的循环 + 256 元素 PE 状态"能否在 7.300 ns 内通过，以及 PV/行和阶段能否共用同一循环结构。**必须靠一次 CSynth 实测**。

### 建议 B（次选，置信度 **medium**）：保留 `runPeArray` 函数但让流水体变成"一 bank 一条直线"

- 把 `#pragma HLS UNROLL` 从 `bank` 循环上**拿掉**，把 `runPeArray` 的 `PIPELINE` 改成只覆盖单 bank 的小函数（每 bank 固定 `PE_BANK_NODES` 个 PE），bank 之间用外层循环串行。每 bank 的数组形参固定一维长度。
- 这与"已试过 (a) 行 bank 分组"的区别在于：**(a) 失败是因为 bank 循环仍被 `UNROLL`（`#pragma HLS UNROLL` 就在 107-108 行）**，所以 16 个 bank 又合成一个巨型单拍体，等于没拆。真正要做的是**让 bank 循环成为流水的迭代维度**，即"每拍只调度一个 bank"。
- 依据：UG902 "pipelining the inner-most loop gives the smallest hardware" + "被流水层级以下循环必须完全展开" **[文档]**；AutoSA 把大阵列切成子阵列 tiling **[论文]**。
- 风险：bank 循环一旦成为流水迭代体，**bank 函数的调用会被共享（一个物理实例）**，这正是 AGENTS.md 要求的"唯一 256-PE 阵列"；但若工具把它 outline 成 16 份则会违反单阵列约束 —— 必须查 `ALLOCATION`/RTL 实例数。
- 缺什么证据：Vitis 2024.2 对"循环里调用 `INLINE off` 子函数 + 一维数组形参"是否仍会复制实例。

### 建议 C（结构方向，置信度 **medium**）：`D×P` 矩形阵列 + 行尾归约树（把归约维度移出物理维度）

- 即 `PROJECT_CONTEXT.md#15.2` 已记录的方向。它解决的问题是**归约跨物理 PE**（row-max/row-sum 要跨列走线），从而消掉每拍大量跨 PE 的条件选择逻辑。
- 论文支持：SWAT 对"方阵 tiling 不适合 row-wise softmax"的批评 **[论文]**；SALO 在方阵里用横向 ripple 和 + 行尾求倒数再广播来绕开 **[论文]**。
- **但请注意**：这一条**不能单独保证 204-65 消失**。若新的 `D×P` 阵列仍然是"函数级流水 + 全展开"，一样可能触发同样的调度失败。**建议 C 必须叠加建议 A/B 的"小循环流水"形态才有效。**
- 风险/缺口：PV 需要 V 以转置顺序流入，可能需要 P 个读端口（BRAM 端口爆炸）；fp32 累加路径能否打 7.300 ns 只能实测；最强先例 SALO 是 ASIC **[论文]**，其结构在 HLS 上未必可流水。

### 建议 D（不推荐）：继续用"节点数组 + 1-D node 调用"的形式化拆分

- 已由 `cf11987` 证实无效（4×4 通过、16×16 仍报 204-65）。这与 UG1399 p.93 "This issue is typically caused by arrays" 一致：**换数组形状/换传递方式不改行为图规模**。

### 建议 E（最保守）：退回已验收的 streaming/systolic 形态

- `fsa_stream` 的 R×C 阵列 + C 个 CMP + 单 C-lane Accumulator 已经过完整 CoSim（`PROJECT_CONTEXT.md#3.2`），且官方库 gemm_hls / Vitis BLAS 都是这个形态。若 16×16 全并行在 7.300 ns 与单阵列约束下无法成立，这是最有工程先例的退路，但要放弃 Split-D 的"每 PE 一个 score_acc"语义。

## 7. 一句话结论

`SCHED 204-65` 是"流水体（= 被完全展开的函数体）的行为图对调度器太大/太杂"的失败出口，官方文档层面可确证的因果链是**流水层级越高 → 下层全部展开 → 需要同时调度的运算与数组访问越多 → 越可能放弃**；D=16 相对 D=4 的质变是**跨边界数组端口位数 × 选择器规模**，不只是 MAC 数。要在**保持唯一 256-PE 阵列**的前提下恢复 II≤5，最可能有效的最小改动是**把"函数级流水 + 全部展开"改成"每个 PE 每拍做固定小事的紧凑循环流水"（建议 A），或让 bank 循环真正成为流水的迭代维度（建议 B）**；`D×P` 矩形阵列（建议 C）是消除跨 PE 归约的长期正确方向，但它必须叠加 A/B 的形态才可能同时解决 204-65。置信度：A medium-high，B medium，C medium，D 已证伪，E 高（作为退路）。
