## 1 任务与验收口径

### 1.1 目标

实现一个参数化 `D×D` 方阵的 Split-D attention 研究顶层 `fsa_stream_split_d`，要求与 `FSA-main`(Chisel) 的 FSA 语义一致：

- 单次顶层调用完成**一次完整 attention**（核内 DMA 搬 Q/K/V/O，不依赖外部多次调用拼装）；
- 只有**一套** `D×D` PE 阵列与**每列一条** Accumulator 通路；QK、softmax 相关步骤、PV **顺序复用**同一套阵列；
- 每个 PE 只有两个寄存器：一个 FP16 `reg` + 一个 FP32 `score_acc`；
- 阵列外**不允许**保存完整的 S/P 副本。

### 1.2 两档配置

| 档位 | 参数 | 阵列 | `DIM_BLOCKS=head/D` | 说明 |
|---|---|---|---|---|
| 默认档 | `FSA_SPLIT_D_PE_DIM=4`、`FSA_SPLIT_D_HEAD_DIM=16` | 4×4 = 16 PE | 4 | **已验收通过**（本文第 9 节） |
| 目标档 | `FSA_SPLIT_D_PE_DIM=16`、`FSA_SPLIT_D_HEAD_DIM=128` | 16×16 = 256 PE | 8 | **未通过**（本文第 10–11 节） |

`PE_DIM` 同时是 **PE 阵列边长**、**每个 tile 的 token 数**、**每轮消费的特征数**；`HEAD_DIM` 是完整 Q/K/V 向量维度。

### 1.3 硬约束（不可放宽）

- 器件 `xcvu37p_CIV-fsvh2892-2-e`、时钟 **10.0 ns**、`set_clock_uncertainty 2.7`，**估算周期必须 ≤ 7.300 ns**。不允许改这三项来换时序。
- 不修改 `FSA-main`；不改生产顶层 `fsa_stream` 的接口与行为。
- Q/K/V/O 四个 64-bit AXI master bundle + AXI-Lite 控制接口保持现状。
- 不得用复制阵列 / 复制 Accumulator / 关闭流水 / 虚假依赖声明（`DEPENDENCE ... false`）来换吞吐。
- 精度合同（第 7 节）不得放宽。
- 服务器测试**只允许**仓库自带入口（第 12.1 节），禁止自定义 wrapper / 替代 Tcl / 临时 testbench。

## 3 顶层结构与数据流

### 3.1 顶层签名（`fsa_stream_split_d.cpp`）

```cpp
void fsa_stream_split_d(
    const fsa::dma_word_t q_address[MAX_QKV_WORDS],
    const fsa::dma_word_t k_address[MAX_QKV_WORDS],
    const fsa::dma_word_t v_address[MAX_QKV_WORDS],
    fsa::dma_word_t o_address[MAX_O_WORDS],
    const ap_uint<32> sequence_length,
    const bool causal,
    ap_uint<8>& status
);
```

- Q/K/V 各占一个 `m_axi` bundle（`q_gmem`/`k_gmem`/`v_gmem`，`num_read_outstanding=16`、`max_read_burst_length=64`、`max_widen_bitwidth=512`、`latency=64`）；
- O 占 `o_gmem`（`num_write_outstanding=8`）；
- 其余端口与 `return` 挂 `control`（AXI-Lite）；
- 行为：`status=1`；`length==0 || length>MAX_SEQUENCE_LENGTH` 时直接返回（**不写 O**，测试台有用例验证这一点）；否则调用 `split_d::run(...)` 后 `status=0`。

### 3.2 控制流骨架（`runController`，`split_d_controller.cpp:74`）

```text
for query_tile in 0..query_tiles-1:            // 每个 tile 处理 PE_DIM 个 query
    load Q tile (query_base, active_queries)
    running_max/running_sum/history_valid 初值
    for key_tile in 0..key_tiles-1:            // causal 时 key_tiles = query_tile+1
        load K tile, V tile
        初始化 pe[][].reg / score_acc / score_valid
        [A] QK 累加        → runPeAccumulateTile
        [B] tile 内 row-max 与 running max 更新
        [C] alpha = exp2(scale*(running_max - next_max))   （复用列 Accumulator 的 PWL）
        [D] score 从 fp32 转 fp16 写回 pe.reg（score_valid 屏蔽）
        [E] SUB_MAX：pe = score + (-next_max)
        [F] SCALE：pe = pe * attention_scale
        [G] PWL 8 段扫描求 exp2 → 写回 pe.reg（概率 P）
        [H] ROW_SUM：runPeRowSum → running_sum = alpha*running_sum + row_sum
        [I] PV：pe → pv_sum，再 output_acc = alpha*output_acc + pv_sum
        running_max/history_valid 更新
    归一化 (inverse_sum × output_acc) → storeOutputTile
```

### 3.3 PE 坐标约定（**重要，容易看反**）

`pe[row][col]` 中：

- **`row` = key 维**（来自 K/V tile 的行）；
- **`col` = query 维**（来自 Q tile 的行）。

因此 `pe[row][col].score_acc` = `S[key=row][query=col]`，而 Q/K 装载时用 `k_tile[row][feature]`、`q_tile[col][feature]`（`split_d_compute.cpp:163-168`）。列方向（`col`）是**每个 query 一条**的归约方向：ROW_SUM、running_sum、output_acc、归一化都按 `col` 独立进行。

### 3.4 tile 与掩码

- `active_queries = min(remaining_queries, PE_DIM)`，`active_keys` 同理 → **尾 tile 用掩码而非改阵列规模**。
- `score_valid[row][col] = (col<active_queries) && (row<active_keys) && (!causal || global_key<=global_query)`（`split_d_controller.cpp:160-163`），其中 `global_key=key_base+row`、`global_query=query_base+col`。**因果掩码是"含对角"的（`<=`）**。
- `score_valid` 是后续所有阶段唯一的有效性判据：无效元素的 `pe.reg` 被强制写 0，避免污染 PWL 与 PV。

## 4 PE 阵列：物理实现

### 4.1 物理资源

- **恰好 `PE_DIM × PE_DIM` 个 PE**（4×4→16，16×16→256）。
- 每个 PE 的算法状态（`split_d_types.hpp:20`）：

  ```cpp
  struct PeState{
      elem_t reg{};        // FP16：先存 Q 元素，后存 softmax 概率 P
      acc_t  score_acc{};  // FP32：QK 累加期间保存同一个 S 元素
  };
  ```

- **每列一条 Accumulator**（`accUnit`，FP32×FP32+FP32），由 `runAccumulatorColumns` 对 `PE_DIM` 个列并行执行。

### 4.2 当前阵列函数 `runPeArray`（`split_d_compute.cpp:90`）

```cpp
void runPeArray(
    const PeState pe[PE_DIM][PE_DIM],
    const elem_t operand_b[PE_DIM][PE_DIM],
    const acc_t  operand_c[PE_DIM][PE_DIM],
    const bool   exp2_mode,
    PeMacUnitOutput result[PE_DIM][PE_DIM]
){
    #pragma HLS INLINE off
    #pragma HLS PIPELINE II=PE_ARRAY_II style=stp
    #pragma HLS ARRAY_PARTITION variable=pe complete dim=0
    #pragma HLS ARRAY_PARTITION variable=operand_b complete dim=0
    #pragma HLS ARRAY_PARTITION variable=operand_c complete dim=0
    #pragma HLS ARRAY_PARTITION variable=result complete dim=0

    for(int row=0; row<PE_DIM; ++row){
        #pragma HLS UNROLL
        for(int col=0; col<PE_DIM; ++col){
            #pragma HLS UNROLL
            result[row][col] = peMacUnit(
                pe[row][col].reg, operand_b[row][col],
                operand_c[row][col], exp2_mode
            );
        }
    }
}
```

**关键设计点（这是当前唯一被验收通过的形状）**：

1. `row`/`col` 由双层 `UNROLL` 展成**编译期常量**，因此 `result[row][col]` 的写回索引是常量，写回路径上**没有随循环变量变化的选择器**。
2. 整个阵列在**同一个流水体**内原地求值，没有 bank 循环、没有 `node_*` 中间数组、没有额外的寄存级函数。
3. `PE_ARRAY_II` 由规模决定（`split_d_internal.hpp:45-49`）：`PE_DIM<=4 ? 1 : 5`，可用 `-DFSA_SPLIT_D_PE_ARRAY_II=<n>` 覆盖。
4. `peMacUnit(reg, b, c, exp2_mode)`（`include/fsa/stream/arithmetic.hpp:47`）同时覆盖两种用途：
   - `exp2_mode=false`：普通 MAC → 结果在 `out_accType`（FP32）与 `out_elemType`（FP16）两个字段；
   - `exp2_mode=true`：PWL exp2 分段求值 → 结果在 `out_elemType`，并输出 `out_exp2` 表示该分段是否命中。

### 4.3 单一阵列的唯一调用点（约束如何被保证）

源码里 `runPeArray` **只有一处定义**，且被**三个**函数调用，全部在 `split_d_compute.cpp` 内：

| 调用者 | 位置 | 用途 |
|---|---|---|
| `runPeAccumulateTile` | `split_d_compute.cpp:173` | QK：一个 key tile 的全部累加 |
| `runPeRowSum` | `split_d_compute.cpp:222` | ROW_SUM：P 的逐行累加 |
| （控制器 4 处直调） | `split_d_controller.cpp:256 / 278 / 307 / 394` | SUB_MAX / SCALE / PWL / PV |

控制器用显式约束保证只有一个物理实例：

```cpp
#pragma HLS ALLOCATION function instances=detail::runPeArray limit=1          // controller:83
#pragma HLS ALLOCATION function instances=detail::runAccumulatorColumns limit=1  // controller:84
```

**注（`Confirmed`）**：P3a 之后 `peBankMacUnit`（`split_d_compute.cpp:51`）与 `stagePeArrayResult`（`split_d_compute.cpp:9`）**已无调用点**，属于待清理的遗留物（保留定义不影响综合）。

### 4.4 已尝试过的其它阵列形状（**不要重复**）

| 形状 | 4×4 顶层估算 | 16×16 | 结论 |
|---|---|---|---|
| **当前：整阵列单流水体** | **7.300 ns** ✓ | 未测 | **采用** |
| 单 bank + 独立 `stagePeArrayResult` 寄存级 | 7.300 ns ✓ | CSynth 失败（`SCHED 204-65`） | 4×4 可用，16×16 不可 |
| rolled bank 循环（结果经 `node_staged` 写回） | 7.893 ns ✗ | 数值通过、7.934 ns ✗ | `Rejected`：写回索引成为循环变量，多出选择逻辑 |

| 给 bank 函数加 `LATENCY min=1 max=1` | **20.851 ns** ✗✗ | — | `Rejected`：把 bank 调用串行化 |

## 5 四个阶段的实现细节

### 5.1 QK 累加 —— `runPeAccumulateTile`（`split_d_compute.cpp:135`）

```cpp
#pragma HLS INLINE off
for(int block=0; block<DIM_BLOCKS; ++block){
    for(int lane=0; lane<PE_DIM; ++lane){
        #pragma HLS PIPELINE II=5
        const int feature = block*PE_DIM+lane;
        elem_t operand_b[PE_DIM][PE_DIM];   // 本迭代私有
        acc_t  operand_c[PE_DIM][PE_DIM];   // 本迭代私有
        PeMacUnitOutput pe_result[PE_DIM][PE_DIM];
        // ... 装 reg=q_tile[col][feature], operand_b=k_tile[row][feature],
        //     operand_c=pe[row][col].score_acc
        runPeArray(pe, operand_b, operand_c, false, pe_result);
        // ... pe[row][col].score_acc = pe_result[row][col].out_accType
    }
}
```

- 语义：`S[row][col] += sum_{d in this lane} K[row][d]*Q[col][d]`，共 `DIM_BLOCKS × PE_DIM = HEAD_DIM` 个特征、按 `block`→`lane` 顺序累加，**FMA 顺序固定**。
- 越界屏蔽：`col<active_queries` 才装 Q，`row<active_keys` 才装 K，否则装 0。
- 设计意图：把 `block/lane` 循环与 `operand_*` 数组收进函数内部，使**跨迭代不再共享数组**（此前放在控制器里导致 `operand_c` 出现 distance=1 的 store→load 真依赖）。**实测（`Confirmed`）**：这一步让 4×4/16 的 II 全部达标，但**对 16×16 的 II 无效**（见 10.3）。

### 5.2 ROW_SUM —— `runPeRowSum`（`split_d_compute.cpp:196`）

对 `row = 0..PE_DIM-1` 逐行把 `pe[row][col].reg`（即 P）与 1 做 MAC，累加到 `row_sum[col]`：

```cpp
operand_b[r][col] = elemOne();
operand_c[r][col] = (r==row) ? row_sum[col] : accZero();
runPeArray(pe, operand_b, operand_c, false, pe_result);
row_sum[col] = pe_result[row][col].out_accType;
```

`row_sum[col] = Σ_row P[row][col]`，即每个 query 的概率归一化分母（本 tile 部分）。

### 5.3 softmax（控制器内联，`split_d_controller.cpp:180-332`）

顺序固定为：**tile row-max → running max 合并 → `alpha` → 转 FP16 → SUB_MAX → SCALE → PWL exp2 → ROW_SUM**。

- **tile max**：只对 `score_valid` 为真的元素用组合位序比较 `finiteAccMax`（`controller.cpp:39`）求最大；`has_value` 区分"整列无效"。
- **`alpha`（online rescale 系数）**：`alpha = exp2(scale*(running_max - next_max))`。实现上复用列 Accumulator 的 PWL 通路，分两步：

  ```cpp
  runAccumulatorColumns(false, acc_a /*=scale*/, acc_b /*=old-new*/, acc_c, acc_result);
  runAccumulatorColumns(true,  acc_result, acc_b, acc_c, alpha);   // exp2 模式
  ```

  随后按历史状态覆盖：`!history_valid → alpha=0`；`history_valid && !tile_has_value → alpha=1`。
- **SUB_MAX**：`pe.reg = score + (-next_max)`（`operand_b=1`，`operand_c=-next_max`）。
- **SCALE**：`pe.reg = pe.reg * attention_scale`，`attention_scale` 是 `log2(e)/sqrt(HEAD_DIM)`，以 FP16 位模式常量给出。
- **PWL exp2（8 段）**：`split_d_controller.cpp:292-332`（`probability_ready` 初值在 292，分段扫描循环在 294–323）。逐 `piece` 顺序扫描全部 8 个分段，每段调用一次 `runPeArray(..., exp2_mode=true)`：

  ```cpp
  for(int piece=0; piece<exp2PWLPieces; ++piece){
      #pragma HLS PIPELINE II=1
      // operand_b = EXP2_SLOPES[piece], operand_c = exp2PWLIntercept(piece)
      runPeArray(pe, operand_b, operand_c, true, pe_result);
      // 命中分段且尚未就绪 → pe.score_acc = (acc_t)out_elemType; probability_ready=true
  }
  ```

  设计意图：`pe.reg` 在整段扫描期间**保持原始 X 不变**，命中结果暂存到已不再需要 S 的 `pe.score_acc`，避免分段之间产生依赖链。8 段的斜率常量在 `controller.cpp:15-24`。

### 5.4 PV（`split_d_controller.cpp:348-429`）

- `PV_INTERLEAVE = 8`（`split_d_internal.hpp:15`）：把 head 维分成每 8 个 feature 一组，**8 个独立上下文交错发射**。
- 单一**扁平**调度循环，先做 `PV_INTERLEAVE × PE_DIM` 次 PE 操作，再做 `PV_INTERLEAVE` 次列 Accumulator 更新：

  ```cpp
  #pragma HLS PIPELINE II=1
  #pragma HLS DEPENDENCE variable=output_acc inter false
  #pragma HLS DEPENDENCE variable=pv_sum inter RAW distance=8 true
  ```

  - `pv_sum[context][col]` 用 8 个独立上下文，使同一上下文的反馈距离为 8（真实依赖，声明为真）；
  - `output_acc` 声明 `inter false`：它只在循环尾部的 Accumulator 更新里被读写，且那个写与下一次同 feature 的读之间隔着完整的 group 迭代，属**已确认安全的假相关**。
  - 设计意图：避免工具为外层 feature-group 另建 outline 层级而**复制 PE 阵列**（这是历史上真实发生过的失败）。
- 累加形式：`output_acc[col][feature] = alpha[col]*output_acc[col][feature] + pv_sum[context][col]`。

### 5.5 归一化与回写（`split_d_controller.cpp:440-469`）

```cpp
reciprocalColumns(running_sum, inverse_sum);      // 1/l，分母为 0 时输出 0
for(feature = 0..HEAD_DIM-1)
    normalized[col][feature] = inverse_sum[col] * output_acc[col][feature];   // 走列 Accumulator
storeOutputTile(o_address, query_base, active_queries, normalized);
```

## 6 DMA 与存储接口

| 函数 | 位置 | pragma 要点 |
|---|---|---|
| `loadElemTile` | `split_d_dma.cpp:7` | `INLINE`（强制内联，**不生成独立 RTL 模块**——这是历史上修复 Q/K/V 事务错位的关键） |
| `loadValueTile` | `split_d_dma.cpp:35` | 同上，但**转置顺序**装载 V（PV 需要 `v_tile[r][feature]` 按行取 V 的第 `feature` 个分量） |
| `storeOutputTile` | `split_d_dma.cpp:63` | `INLINE off`，内部 `PIPELINE II=1` |

- 存储字宽：Q/K/V 每 token `HEAD_DIM/4` 个 64-bit word（FP16×4）；O 每 token `HEAD_DIM/2` 个 word（FP32×2）。
- 顶层 DMA 深度按 `MAX_SEQUENCE_LENGTH × HEAD_DIM / 4`（QKV）与 `/2`（O）计算（`split_d_config.hpp:20-28`），并在 `run_hls.tcl` 里与 `-D` 宏保持一致。
- **历史教训（`Confirmed`）**：`loadElemTile`/`loadValueTile` 一旦被综合成独立子模块，就会在跨事务之间复用同一份硬件状态，导致 V tile 滞后一个事务、输出错误。修复方式是对它们**强制 `INLINE`**（无子模块报告）。修改这两个函数时务必复查"RTL 里是否存在 `loadElemTile`/`loadValueTile` 模块"。

## 10 16×16/128 的现状：已完成的部分与未通过的判据

### 10.1 已经解决的两个问题（`Confirmed`）

| 问题 | 根因 | 修法 | 结果 |

### 10.3 为什么"把累加搬进函数"解决不了 16×16 的 II（`Confirmed`）

尝试（commit `f9f0638`）把 QK/ROW_SUM 的内层循环与 `operand_*` 数组移入 `runPeAccumulateTile`/`runPeRowSum` 后，Vitis 的原文警告变成：

```text
WARNING: [HLS 200-880] in module 'runPeAccumulateTile' (loop VITIS_LOOP_175_1_VITIS_LOOP_176_2):
  carried dependence (II=5, distance=1) store 'operand_c_write_ln196' -> load 'operand_c_load_1'
WARNING: [HLS 200-880] in module 'runPeRowSum' (loop VITIS_LOOP_231_1):
  carried dependence (II=5, distance=1) store 'row_sum_write_ln255' -> load 'row_sum_load_1'
WARNING: [HLS 200-875] II = 6 is infeasible due to multiple pipeline iteration latency = 8
  and incompatible II = 5 of 'call' operation to 'runPeArray'
```

**结论**：受限的是**流水迭代延迟（8 拍）**，而不是 `Target II` 这个数字——工具明确说 II=6、II=7 都不可行。也就是说：**只要流水体内还有一次需要 8 拍完成的 `runPeArray` 调用，II=5 在物理上就不可达**。改变数组作用域、把循环搬家都无法绕过这一条。

### 10.4 P3a 为什么可能改变 16×16 的结论（`To verify`）

P3a 把 `runPeArray` 的一次求值延迟从 **7 拍降到 3 拍**（4×4 实测：

| 版本 | `runPeArray` latency |
|---|---|
| rolled bank 形状 | 7 拍 |
| **当前（整阵列单流水体）** | **3 拍** |

`200-875` 的约束正是"调用延迟须能被 II 覆盖"。3 拍远小于 5 拍的目标 II，所以**P3a 有可能直接把 16×16 的 QK/ROW_SUM II 拉到 5**——但**从未在 16×16 上验证过**（用户已指示暂时搁置）。这是恢复 16×16 工作时**第一件该测的事，且零代码改动**。

### 10.5 已排除的做法（**不要重复**）

| 做法 | 结果 | 约束 |
|---|---|---|
| bank 循环带 `UNROLL` | 所有 bank 合成单个巨型单拍体 → `204-65` | bank 循环必须保持 rolled（若采用 bank 形状） |
| 把 bank 做成独立函数、一维数组形参 | 4×4 的 CSim 直接输出全 0 | 一维数组形参的 bank 函数不可用（`ecdc987`） |
| 给 `runPeArray` 固定 `PIPELINE II=5` | 16×16 仍报 `204-65`；且 4×4 回退（7.434ns、II 退化） | 间隔必须按规模自适应 |
| 用固定规模"节点数组"限制跨函数数组规模 | 4×4 通过，16×16 仍 `204-65` | `cf11987` 路线的上限 |
| 把 bank 粒度改成 2 行或 1 行 | 4×4 全部通过 → 证明"rolled 次数/写冒险"不是根因 | 故障**只在 `PE_DIM=16` 出现**，属规模相关 |
| 给 bank 函数加 `LATENCY min=1 max=1` | 4×4 顶层恶化到 **20.851 ns** | 会串行化 bank 调用 |

## 11 16×16 的构建方案（候选与判据）

### 11.1 关于"204-65"的实测规律（`Confirmed`）

| 形状 | 单拍体内展开的 PE 数 | `204-65` |
|---|---|---|
| 4×4 整阵列单流水体 | 16 | **从未出现** |
| 16×16 扁平数组 + `complete dim=0` | 256 | 出现（`cf11987` 的 16×16 尝试） |
| 16×16 四行 bank + bank 循环带 `UNROLL` | 64 | 出现（`c6a222a`） |

`Current assessment`：触发条件与**单拍体内展开的 PE 数量 / 跨函数边界的端口规模**强相关，与"是否存在 bank 循环"弱相关。官方文档对此只有一句定性说明（UG1399："This issue is typically caused by arrays"），`204-65` **没有官方量化条目**。

### 11.2 候选方案（按代价从低到高）

#### 方案 A（**首选，零代码改动**）：直接测当前形状的 16×16

- 命令：`FSA_SPLIT_D_PE_DIM=16 FSA_SPLIT_D_HEAD_DIM=128 ./run_hls.sh fsa_stream_split_d`
- 唯一变化：`runPeArray` 求值延迟 7→3 拍、写回索引变常量。
- **期望**：QK/ROW_SUM 的 II 从 8 降到 5；顶层时序从 7.934 ns 改善（写回选择器消失）。
- **风险**：单拍体内展开 256 个 PE 可能**重新触发 `204-65`**（对照见 11.1：256 PE 的扁平形状历史上报过该告警）。若 CSynth 超过 60 分钟未完成，立即中断并读 `csynth_design_size.rpt`。
- 判据：`204-65`=0、QK/ROW_SUM II=5、PWL/PV II=1、顶层 ≤7.300 ns、7/7 CoSim 通过、RTL 层次显示 PE=256/Acc=16 无副本。

#### 方案 B（若 A 复发 `204-65`）：分次调用同一阵列

- 把整阵列求值拆成 **2 次调用**，每次覆盖一半（例如 `PE_BANK_ROWS = PE_DIM/2`，两次 `runPeArray` 各处理一半行），仍是**同一个** `runPeArray` 实例（`ALLOCATION limit=1`），**不复制阵列**。
- 依据：64 PE 展开历史上也报过 `204-65`，所以拆分粒度需要实验确定（从 4 行/bank 起试，必要时降到 2 行）。
- 风险：每次调用 8 拍 → 每 tile 延迟可能上升到 `2×8=16` 拍；须实测 II 与延迟。
- 判据同上，并额外用 RTL 层次报告确认只有 1 个 PE 阵列。

#### 方案 C（结构性）：`D×P` 矩形阵列 + 行尾归约树

- 让"并行维度 = 互相独立的 query 行"、"归约维度 = 同一行内的 key/head 元素"，把 row-max/row-sum 从"跨物理 PE 边界"移到**行尾小归约树**。
- 文献支持：SWAT(DAC'24) 批评方阵——"the systolic array's square structure requires square tiling ... This suboptimal for row-wise SoftMax operations"。
- `D=16, P=16` 仍是 256 PE；`head=128` 时变成 `8` 次串行累加进同一累加器，**开销不随 D² 增长**。
- 风险：这是**架构变更**（阵列形状、归约位置、PE 内部状态都要动），需要用户明确同意；且 SALO 是 ASIC 实现，HLS 可流水性**无先例证据**。

#### 方案 D（退路）：回到 systolic / streaming 形态

- 生产基线 `fsa_stream` 的 `R×C` systolic + CMP + 单 C-lane Accumulator **已通过完整 CoSim**，是已证可行的形状。
- 代价：放弃"每 PE 一个 `score_acc`"的 Split-D 结构语义。

### 11.3 与文献/官方资料的一致性检查（`Confirmed`，来自已归档调研）

- **官方**：`#pragma HLS DEPENDENCE variable=<arr> inter false` 的语义是"不加时编译器默认假设存在跨迭代依赖，于是以更大的 II 调度"。
- **官方**：UG902 Code Style 指出"When a loop or function is pipelined, ... unrolls all loops in the hierarchy below"，且"If there is a loop with variable bounds in this hierarchy, it prevents pipelining"。
- **公开项目中 ≥256 PE 的 Vitis HLS 2D 阵列可流水实现：未找到先例。** spcl/gemm_hls 用 1D PE 链 + `Stream<>` + `DATAFLOW`；AutoSA 用 tiling factor + strip-mine；ViT-Accelerator 用逐拍位移的 16×16。这是需要向用户如实说明的限制，不应假装已有成熟解法。

### 11.4 建议的推进顺序

1. **先做方案 A**（零代码），它是唯一能直接验证"3 拍延迟是否解开 II=5 约束"的实验；
2. 若 A 的数值或 II 不达标，**先用消融定位**：V0 单 PE 纯 MAC → V1 只保留 QK 的阵列（无 softmax）→ V2 加行尾 row-max → V3 加 online rescale + exp2 → V4 复用同阵列做 PV → V5 全 kernel + DMA。**V1 与 V3 的对比是关键判据**：若 V1 能流水而 V3 不能，锅在 softmax 的数据依赖；若 V1 就不能，锅在阵列规模本身。
3. A/B 都失败再考虑 C，并把"这是架构变更、HLS 无先例"如实报告。
