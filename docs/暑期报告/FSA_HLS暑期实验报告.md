# FSA 注意力加速器 HLS 实现与 NM37 板级验证

## 摘要

本项目围绕注意力计算的 FPGA 实现开展暑期研究与工程工作。前期依次阅读《Attention Is All You Need》、FlashAttention、FlashAttention-2 和 FSA，梳理注意力计算、分块与在线 softmax、并行工作划分及单阵列复用之间的关系，并聚焦 FSA 原工程的 Scala/Chisel 硬件部分开展调研。在此基础上，逐步完成基础计算模块、片上存储、ExecutionPlan、请求级控制和 DMA 顶层的 HLS 实现。

本次提供的工程快照采用默认 4×4 脉动阵列，元素类型为 FP16，累加及输出类型为 FP32。当前 `fsa_dma_top` 源码包含查询块与键值块两层调度，一次启动完成指定长度序列的注意力计算，输入 Q/K/V 和输出 O 采用按行存储布局，四个地址参数共享一个 64-bit AXI4 主接口。

据包内 DMA 综合总结，2026 年 8 月 24 日的一次构建完成了 `L=9、D=4、causal=false` 用例的 C 仿真、C 综合与单事务 RTL 协同仿真；该构建使用 303 个 DSP、105,648 个 FF、128,957 个 LUT 和 4 个 BRAM_18K，RTL 单事务延迟为 27,566 个周期。以上为历史构建总结记录，与当前压缩包及最终上板 IP 的版本对应关系仍需补齐。

工作初稿记录 NM37 固定向量上板测试已经通过，本文保留这一阶段工作结论，并在第五章标记其执行日期、IP 版本、实现后报告和 VIO/ILA 记录的待补位置。完整主机数据通路、部署软件栈及真实应用负载尚未形成经验证的系统闭环；DATAFLOW 重构仍作为后续研究方向。[S01、S07]

**待补：**报告年月和工作时间范围【M01】；最终仓库版本【M02】；板测结果归档【M03、M04】。

## 第一章 项目背景、目标与阶段完成概况

### 1.1 项目背景与研究问题

缩放点积注意力的基本形式为：

$$
S=\frac{QK^T}{\sqrt{D}},\qquad P=\operatorname{softmax}(S),\qquad O=PV.
$$

序列长度增大时，显式保存分数矩阵与概率矩阵会增加存储占用和数据搬运。FPGA 实现还需要协调有限片上存储、存储访问端口、阵列输入波前、softmax 归约以及跨块状态更新。因此，本项目既关注矩阵运算，也关注数据布局、状态保存与控制调度。

### 1.2 暑期目标及工作范围

暑期工作目标包括：理解注意力与 IO 感知分块方法；分析 FSA 的 Scala/Chisel 架构；建立可综合的 HLS 模块与分层验证路径；实现请求级和 DMA 顶层；把计算 IP 接入 NM37 Vivado 工程并完成固定向量验证。

对原工程的调研范围限定于 PE、CMP、Accumulator、SRAM、ExecutionPlan、Delayer 和 Controller 等 Scala/Chisel 硬件结构。完整主机软件与应用系统部署不属于初稿所述已经完成的验收范围。

### 1.3 技术路线与工作组织

工作依次经历算法学习、原始架构调研、模块迁移、核心逐级集成、DMA 完整序列计算及 NM37 固定向量验证。HLS 迁移采用自底向上的组织方式，先建立类型和状态规范，再连接数据通路与控制逻辑，以模块测试和阶段实验缩小错误定位范围。

## 第三章 技术方案与已完成实现

### 3.1 算法基础与架构选择

| 阅读内容 | 对本项目的直接作用 |
|---|---|
| Attention Is All You Need | 明确 QK、按行 softmax、PV、缩放与 causal mask 的计算关系 |
| FlashAttention | 理解分块和在线更新如何减少中间注意力矩阵的保存与搬运 |
| FlashAttention-2 | 关注非矩阵操作、共享状态和工作划分对实际效率的影响 |
| FSA | 研究单一脉动阵列跨注意力阶段复用，以及控制、存储和波前的具体组织 |

对同一查询行，在线 softmax 跨键块维护最大值 m、指数和 l 及未归一化输出向量。遇到新块时，以新的最大值对旧状态重新缩放，再合并新块贡献，最后进行输出归一化。这个过程决定了 CMP、Accumulator 和片上状态存储的功能需求。

### 3.2 数值类型与迁移策略

当前实现使用混合浮点精度：Q/K/V 等元素采用 FP16，累加和输出采用 FP32。

指数相关运算使用 8 段 PWL 近似；缩放与指数换底常量在编译期生成：

$$
\alpha=\frac{\log_2 e}{\sqrt{D}},\qquad
\exp_2((s-m)\alpha)=\exp((s-m)/\sqrt{D}).
$$

公式说明的是理想等价关系；实际结果仍受 FP16/FP32 精度及 PWL 近似影响。

迁移采用 `current/next` 状态模型：一个逻辑步读取当前状态、生成下一状态，再统一提交。

### 3.3 基础模块实现

| 模块 | 当前实现内容 | 主要位置 |
|---|---|---|
| PE | 多模式算术、局部状态和邻接传播；调用 MAC、PWL 指数和精度转换 | `src/core/pe.cpp`、`arithmetic.cpp` |
| CMP | 最大值状态、控制命令及掩码相关处理 | `src/core/cmp.cpp`、`execution_plan.cpp` |
| InputDelayer / OutputDelayer | 输入波前组织、反转、延迟及输出对齐 | `src/core/delayer.cpp` |
| Systolic Array | 默认 4×4 的 PE/CMP 组织及控制、数据传播 | `src/core/systolic_array.cpp` |
| Accumulator | scale 状态、乘加、PWL 指数、reciprocal 状态推进与归一化相关操作 | `src/core/accumulator.cpp` |
| Banked SRAM | Scratchpad 与 Accumulator RAM，整行/窄端口、bank 仲裁和响应状态 | `src/core/banked_sram.cpp` |
| ExecutionPlan | 五类指令的逻辑步控制、地址、阶段与有效范围 | `src/core/execution_plan.cpp` |

默认 Scratchpad 配置为 24 行、2 个 bank、每 bank 行内 1 个 sub-bank；Accumulator RAM 为 5 行、2 个 bank、每 bank 行内 2 个 sub-bank。独立 SRAM 综合总结记录其采用小型寄存器/LUT 存储结构，没有使用 BRAM/URAM。



### 3.4 核心集成与请求级控制

当前主路径通过单个请求 FSM 依次完成最大值初始化、Q/K/V 预装、指令执行以及 L/O 读回。不同阶段先产生 `step_input`，再通过同一个静态调用点推进共享的 `advanceDatapath`。

请求接口通过 `initialize` 与 `finalize` 区分首块、中间块和末块：首块建立在线状态；中间块继续复用旧最大值和 L/O；末块执行最终归一化。`active_keys`、`query_base`、`key_base` 用于边界和全局 causal 索引表达。

默认 4×4 阶段总结记录五类指令的逻辑步数分别为：

| 指令 | 历史默认配置的逻辑 step 数 |
|---|---:|
| `LOAD_STATIONARY` | 5 |
| `ATTENTION_SCORE_COMPUTE` | 28 |
| `ATTENTION_VALUE_COMPUTE` | 12 |
| `ATTENTION_LSE_NORM_SCALE` | 17 |
| `ATTENTION_LSE_NORM` | 5 |

### 3.5 DMA 顶层与接口设计

当前 DMA 顶层按查询块、键值块两层循环组织完整序列计算，末块完成后回写有效查询行的 O。外部输入 Q/K/V 均为 `[token][feature]` 的 FP16 行主序；V 在请求核预装阶段组织为内部所需的转置布局。

| 项目 | 当前源码约定 |
|---|---|
| 每个 AXI 数据字 | 64 bit |
| Q/K/V 打包 | 每字 4 个 FP16，lane 0 位于最低 16 bit |
| O 打包 | 每字 2 个 FP32，lane 0 位于最低 32 bit |
| 最终外部输出 | 归一化后的 O；不是旧 README 中的 L＋O 连续区域 |
| `status=0` | 成功 |
| `status=1` | 非法序列长度 |
| `status=2` | 核心协议错误 |
| 序列长度检查 | 拒绝 0 和超过配置上限的长度；分支存在不代表异常用例已经测试通过 |

控制寄存器偏移依据 DMA 综合总结与本包板测控制器整理如下。

| 参数 | 偏移 |
|---|---|
| 控制寄存器 | `0x00` |
| Q 基地址低/高位 | `0x10 / 0x14` |
| K 基地址低/高位 | `0x1C / 0x20` |
| V 基地址低/高位 | `0x28 / 0x2C` |
| O 基地址低/高位 | `0x34 / 0x38` |
| `sequence_length` | `0x40` |
| `causal` | `0x48` |
| `status / status_ap_vld` | `0x50 / 0x54` |

## 第四章 关键问题解决与优化工作

### 4.1 SA 时序调度与流水边界调整

2026 年 8 月 13 日 SA 综合总结比较了两次构建。修改包括把 `peExp2PWL` 固定延迟从 12 拍调整为 13 拍，并把 SA 顶层目标设为 II=16。[S09]

| 指标 | 较早构建，14:55 | 后续构建，15:43 |
|---|---:|---:|
| HLS 估算周期 | 13.966 ns | 7.150 ns |
| 相对 7.30 ns 有效预算的裕量 | -6.666 ns | +0.150 ns |
| 顶层 latency | 15 cycles | 17 cycles |
| 顶层实际 II | 15 | 16 |
| DSP | 137 | 274 |
| FF | 29,610 | 59,266 |
| LUT | 54,564 | 77,960 |

总结记录后一次构建形成 16 个独立 `peMacUnit` 实例，并通过 C/RTL 协同仿真。其主要收益是 HLS 估算时序改善和流水边界形成；代价是资源增加，且顶层 latency 与 II 均有增加。

### 4.2 核内 SA 并行化与系统瓶颈辨析

2026 年 8 月 19 日核心综合总结还记录了另一组历史比较：集成 SA stage 从 II=16 调整为 II=1，PE 等效资源由 8 套扩展为 16 套；整个该核心的 DSP 从 158 增至 300，但普通事务的协同仿真 latency/interval 仍为 68/69 cycles。这一实验说明局部并行度提高后，完整事务仍可能受其他状态、存储和控制环节限制。

### 4.3 Accumulator 四列并行

Accumulator 综合总结记录：通过常量 lane 调用与 `FUNCTION_INSTANTIATE`，将共享计算路径调整为四套空间独立 lane。[S10]

| 指标 | 共享 datapath 构建 | 四 lane 构建 |
|---|---:|---:|
| 综合最大 latency | 80 cycles | 18 cycles |
| 综合最大 interval | 81 cycles | 19 cycles |
| DSP | 10 | 20 |
| FF | 4,711 | 8,236 |
| LUT | 7,067 | 20,633 |

四 lane 构建的 HLS 估算周期为 6.516 ns；`EXP_S2` 的协同仿真 latency/interval 为 17/18 cycles。该优化降低了独立 Accumulator 顶层的最大事务延迟，同时显著增加 LUT。

### 4.5 Banked SRAM 仲裁与访问结构

SRAM 综合总结记录，较早的 Scratchpad RTL 协同仿真曾出现不同 bank 访问不能按预期同时完成的问题。采用固定 bank 仲裁结构后，相关失败消失，`sp_ram_top` 和 `acc_ram_top` 均记录 C/RTL 通过，顶层 latency=1、II=1。

该工作应说明：固定 bank/sub-bank 访问方式与端口展开如何帮助工具表达并行访问，以及同 bank 冲突如何按优先级处理。

### 4.6 多份完整数据通路复制与单核心复用

请求级 2026 年 8 月 21 日综合总结记录，旧请求顶层因预装、清最大值、执行和读回等辅助调用组织，形成 7 套完整数据通路：

$$
7\times340+3=2383\ \text{DSP}.
$$

当前源码使用统一请求 FSM 和一个数据通路调用点，DMA 的 8 月 24 日综合总结记录唯一数据通路为 300 DSP，执行计划为 3 DSP，合计 303 DSP。

| 历史阶段 | 报告顶层 | 完整数据通路结构 | DSP |
|---|---|---|---:|
| 8 月 21 日请求级构建 | `fsa_core_request_top` | 7 套，每套约 340 DSP | 2,383 |

## 第六章 当前能力、限制与遗留问题

### 6.1 当前可用能力

当前源码提供默认 4×4 混合浮点注意力计算路径，包括跨 KV block 在线状态维护、完整序列调度、有效键数量与全局 causal 索引表达、FP16 输入和 FP32 输出打包、非法长度返回分支及请求协议状态。

当前主路径采用顺序请求 FSM，不实现原 Chisel 双 FSM 的 conflict-free 指令重叠，也未接入实验性 `accumulator_pipeline`。DATAFLOW token 流式架构仍属于方案层面的后续方向。

### 6.2 功能、数值和性能限制

- 主 DMA 测试只记录非 causal 单事务；CMP 层的掩码测试不能代替端到端 causal 验证。
- 数值判断使用绝对容差，尚缺误差统计和不同分布、较长序列下的误差分析。
- 当前请求调度受共享状态和函数调度影响，局部 II=1 不代表系统可逐拍接收完整请求。
- 历史 DMA HLS 时序估算裕量为 0 ns。

### 6.3 工程部署尚未闭环的部分

根据初稿，最终外部存储和主机高速传输链路、驱动与运行时、真实应用工作负载均未完成经验证的部署闭环。补充包存在 U280 的 XDMA/HBM 工程脚本和 Python 主机测试程序，因此当前更准确的表述为“已有部分部署方案及代码准备，但未提供执行和系统联调通过记录”，而非“完全没有软件文件”。[S01、S16]

U280 与 NM37 的目标器件不同。U280 准备工程不能作为 NM37 完整系统已经部署的证据，也不自动代表后续最终平台已选定。【M08、M11】

### 8.1 主要成果与工作贡献

本阶段从注意力算法和 FSA 架构出发，形成了模块实现、片上状态、执行计划、请求控制及 DMA 顶层的工程路径。补充材料使阶段成果能够进一步落实到具体源码文件、测试用例和历史综合数据。工作初稿记录的 NM37 固定向量上板通过，是当前阶段的重要硬件验证结果，最终记录将在补齐 IP 版本和板测证据后归档。[S01—S18]

### 8.2 工程经验

1. 状态更新语义是移植基准。保持 `current/next` 的同步语义有助于定位跨模块错误，但性能必须由硬件调度和结果衡量。
2. 功能正确与结构正确需要分别检查。旧请求级构建的完整数据通路复制说明，C/RTL 数值通过也可能伴随显著的非预期资源开销。
3. 局部并行不保证事务加速。SA stage II 改善后，历史核心事务延迟仍可能保持不变；系统瓶颈需要分层定位。
4. 优化需要同时报告代价。Accumulator 四列并行降低独立模块最大事务延迟，但资源上升；DMA 相邻构建改善时序估算，却增加事务周期。
5. 函数名和注释不能替代 RTL 证据。输入“寄存器级”的综合结果为 0 FF，说明物理边界必须以报告和实现确认。
6. 板级功能、最终时序与完整部署是不同层次。固定向量通过能够支撑受控计算路径可运行，但外部存储、主机调用和真实负载仍需要独立闭环。
