**解读**：6 个源码调用点（控制器 SUB_MAX/SCALE/PWL/PV 四个 + `runPeAccumulateTile` + `runPeRowSum`）**全部被汇聚到同一个 outline 流水模块中的同一个实例**。控制器通过 inlining/共享实现这一点，`#pragma HLS ALLOCATION function instances=detail::runPeArray limit=1` 只是约束——**结论来自实例树，不是来自 pragma**。

**2026-10-09补充复核**：逐层唯一实例路径为`fsa_stream_split_d→grp_run_fu_157→grp_runController_fu_102→grp_runController_Outline_VITIS_LOOP_121_3_fu_310→grp_runPeArray_fu_985`；唯一Accumulator实例为`runController/grp_runAccumulatorColumns_fu_875`。已保存16个PE乘法、4个Accumulator乘法及8个FP32减法的实际例化位置，见[实例清单](evidence/split_d_9c49789_4x4/rtl_arithmetic_instances.txt)。RawFMA被内联，乘法器清单及源码映射支持算术通路数量，但不等于完整舍入/状态/存储逻辑均已逐项审计。

| 乘法器 | 例化数 | 含义 |
|---|---|---|

### 3.3 DSP 40 的分解（**自洽**）

| 来源 | DSP | 依据 |
|---|---|---|
| 16个FP16 PE乘法（`mul_11ns_11ns_22`×16） | 16 | 每个实例1DSP，`runPeArray`合计16DSP |
| 4 个 FP32 乘法（`mul_24ns_24ns_48`×4，Accumulator 列） | 8 | `runAccumulatorColumns` 模块 DSP=8 |
| 8个FP32减法（`fsub_32ns_32ns_32_3_full_dsp_1`×8） | 16 | Outline报告及RTL确认，每实例2DSP |
| **小计** | **40** | |
| 顶层实测 | **40** | `run` / `fsa_stream_split_d` 的 `Instance` 行 |

FP32减法有8个实际实例，不能把一个IP模块类型/文件写成一条减法通路。另有比较与精度转换IP；DSP全部归于Instance行，只说明DSP统计来自实例，不证明不存在LUT实现的算术。

**这条分解同时回答了此前的一个疑问**：`runPeArray` 模块自身只有 16 DSP（FP16 乘法），而顶层 40 DSP 中相当一部分来自 **FP32 累加/减法通路**，不是 PE 阵列——所以"用总 DSP 倒推 PE 数"是不成立的（Codex §7 已指出，本次实测确认）。
